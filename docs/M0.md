## 1. 目标

M0 只回答三个问题，不做产品功能：

1. **FEL 真的被重建了吗？** 不是只播 BL，也不是转 P8.1。
2. **Windows 的 `wid` 子窗口路径能拿到 FEL 吗？**
3. **macOS 的 render API 能正确输出吗？** HDR10 可用，或明确退 SDR。

### A3 过程中发现的四个坑

1. **mpv 0.42 在 macOS 上没有 OpenGL GPU context。**
   `video/out/gpu/context.c` 的 `contexts[]` 里没有 Cocoa 条目，
   `--gpu-api=help` 只列出 `auto`，`--vo=gpu` 直接报
   `Failed initializing any suitable GPU context`。
   也就是说 mpv 自己开窗的路在本机构建里不可用，
   **render API 是 macOS 上唯一可行的出画方式**（ADR-0003）。

2. **`MPV_RENDER_PARAM_ADVANCED_CONTROL=1` 在 drawRect 驱动模型下会卡住。**
   现象：VO 已 `reconfig`，但日志停在 `Video source: 0x0`，
   `estimated-frame-number=0`，`vo-configured=no`，draws 只有 3 次。
   改成 `advanced=0` 后立刻正常（`Video source: 1280x720` → 起播）。
   若以后要用 advanced control，必须自己按 `mpv_render_context_update`
   的 flags 驱动渲染，不能靠 `setNeedsDisplay`。

3. **OpenGL 像素格式必须显式要求 core 3.2。**
   不加 `NSOpenGLPFAOpenGLProfile` 时落到 2.1，libmpv 报
   `GLSL version too old`，所有 scaler 被禁用，且
   `need >= OpenGL 3.0 for core rectangle texture support`。

4. **跨线程调 `mpv_get_property_string` 会卡死。**
   在 `dispatch_after` 的普通队列里读属性会挂住；在 mpv 事件线程里读、
   或改用 `mpv_observe_property` 收 `MPV_EVENT_PROPERTY_CHANGE` 才正常。
   验证程序用的是后者。

### 另一条结论：mpv 0.42 没有 `dolby-vision-profile` 属性

`${dolby-vision-profile}` 展开为 `(error)`，`--list-properties` 里也没有。
DV 只能从 `video-params/colormatrix=dolbyvision` 判断“是不是 DV”，
profile 与 FEL/MEL 必须自己解析 RPU（ADR-0005 已修正）。

### 已知限制：P5 在本机渲染成紫色（2026-11-19 实测）

> 后续（2026-11-23）：这节只说明 **legacy `gpu` 后端**的限制。mpv 的 render API
> 现在可以用 gpu-next（[ADR-0011](adr/0011-macos-libmpv-inprocess.md)），
> P5 走 `pl_shader_dovi_reshape()` 后不再偏紫。这里的紫色截图留作回归基准。

**现象**：`samples/p5.mkv` 在 `m0-render` 里能播、帧率正常，但画面整体偏紫红
（人脸皮肤变成洋红）。这不是 bug，是 legacy `gpu` 不做 Dolby Vision 整形。

**证据链**：

| 环节 | 实际值 / 行为 |
| --- | --- |
| 解码输出 | `3840x2160 yuv420p10 dolbyvision/bt.2020/pq/full` |
| 像素编码 | P5 是 IPTPQc2（ICtCp 的有损变体），**没有 HDR10 兼容层** |
| legacy `gpu` | `video/out/gpu/video.c` 在创建纹理前调 `mp_image_params_restore_dovi_mapping()` |
| 该函数 | 把 `repr.sys` 从 `PL_COLOR_SYSTEM_DOLBYVISION` 换回 `sys_orig`（BT.2020-NCL），并恢复原始 primaries/transfer |
| 结果 | IPT 的三个分量被当作普通 Y/Cb/Cr 走 BT.2020 矩阵 → 色相错乱（紫） |
| 正确的路径 | libplacebo `pl_shader_dovi_reshape()` + `enhancement_layer` 合成，只有 **gpu-next** 走这条 |
| 本机 gpu-next（当时） | `--vo=gpu-next` → `Failed initializing any suitable GPU context`（macOS 没有可用的窗口后端） |

**反证实验**：

1. 加 `--vf=format:colormatrix=bt.2020-ncl` 强制成普通 YCbCr 后，画面更紫——
   说明问题在“把 IPT 当 YCbCr”，不是 tone mapping 参数没调。
2. 合成一段带 `bt2020 / smpte2084 / bt2020nc` 标记的普通 HEVC（`out/hdr10-marked.mkv`），
   同一条 render API 管线下色条（红/绿/黄/蓝/品红/青）完全正常，
   日志里只有 `colormatrix=bt.2020-ncl` 与 P5 不同。
   → 管线本身没问题，差异只在 `dolbyvision` 这个色彩系统。

**为什么 P7 / P8.1 不紫**：它们的 BL 是真 HDR10（BT.2020 + PQ + ST 2086），
legacy `gpu` 可以正常按 HDR10 tone map 到 SDR，只是增强层不参与。
P5 是唯一没有 HDR10 回退的 profile，所以只有它在当前路径上是错的。

**范围**：

- A3 验证的是渲染管线（GL 上下文、帧率、丢帧），**不验证色彩**；
- macOS v1 只承诺 HDR10（ADR-0003），P5/P7 的 DV 整形交给 Windows 的 gpu-next；
- 当时想在 macOS 上看 P5 的正确颜色，只能给 mpv 补一整套 GPU 后端；现在走产品路径即可（ADR-0011），
  2026-11-25 用产品路径抓第 11 秒的帧确认肤色正常、不再偏紫；
- 颜色回归样本改用 P8.1（NAS 上 `F1`、`Zootopia 2`），P5 只做“P5 路径存在”的冒烟。

调试用的 `MPV_EXTRA` 环境变量（`apps/macos/m0-render`）：

```bash
MPV_EXTRA='tone-mapping=clip;vf=format:colormatrix=bt.2020-ncl' \
  ./apps/macos/m0-render/m0-render samples/p5.mkv 15
```

判定依据是 `disable_residual_flag=false` + RPU 头 Profile 7 ⇒ **FEL**（不是 MEL）。
另外单独解 EL 首帧确认它有真实残差（不是空 EL）：10bit 均值 525.4、std 1.86，
相对中立值 512 的偏差 `>4` 占 99.999%。

#### A2：EL 确实参与重建

三点 A/B（`fel-ab.sh`，gpu-next；当时用验证构建测的，2026-11-25 产品路径复测 8s 为 49.6 dB）：

| 取样点 | PSNR (avg) | SSIM (All) | 像素差 mean / max |
| --- | --- | --- | --- |
| 4 s | 62.1 dB | 0.99980 | 0.159 / 2 |
| 8 s | 50.8 dB | 0.99973 | 0.658 / 5 |
| 14 s | 62.5 dB | 0.99987 | 0.154 / 2 |

单看这些数很容易误判成「EL 没参与」。三条独立证据推翻它：

1. **配对**：`--msg-level=vf=v` 下 `[el_pair]` 没有出现任何
   `emitting BL … alone` / `dropping stale EL`——所有 BL 都与 EL 配对成功，
   EL 挂到了 `mp_image.enhancement_layer` 上。
2. **合成判定**：临时在 libplacebo `renderer.c` 打印 `compose_el`：
   有 EL 时 `el=0x7000… sys=8(DOLBYVISION) nlq=1 compose=1`；
   加 `--vf=format=enhancement-layer=no` 后 `el=0x0 compose=0`。
   对照链路同样真实有效。
3. **放大残差（历史实验）**：当时写了一个一次性脚本把 libplacebo 的 NLQ 残差
   ×100 后重跑，A/B 变成 **PSNR 26.9 dB / SSIM 0.573 / mean 9.50 / max 115 /
   75% 像素差>2**。若 EL 没进 shader，放大不会改变任何东西。
   该脚本依赖那套验证构建，已随验证构建一起删除；现在用 `fel-ab.sh` 的
   原尺寸 A/B（PSNR≈49.6 dB、`>2` 像素≈1%）作为回归基线。

放大后的差异图是逐块的高频残差，黑边区域全零、没有重影——EL 上采样与对齐正确。

**为什么原尺寸差异这么小**：

- 8 s 是暗场景，SDR 100nit tone map 后几乎没有余量；
- FEL 残差在 PQ 域约 0.02（`deadzone_slope≈0.00195 × rr≈13`），
  落到 8bit SDR 后大部分被量化与 dither 吃掉；
- 本机只有 SDR 显示器，截图也只能是 8bit。

**修正判据**：旧的「PSNR 18–25 dB」是 HDR 域/放大后的经验值，**不适用 SDR 8bit**。
A2 的通过标准（现行）：

- 结构性：`[el_pair]` 全帧配对；加 `--vf=format=enhancement-layer=no`
  （`fel-ab.sh` 的第二张图）后 `[el_pair]` 消失、A/B 出现可测差异；
- 回归基线：`samples/p7-fel.mkv` 第 8 秒，PSNR≈49.6 dB、`>2` 像素≈1%
  （2026-11-25 产品路径实测）。

原尺寸 PSNR 只作内容参考，不作判据。

### 2026-11-19 A5：mpv IPC、控制条、DV 徽标

壳不再依赖视频子窗口的焦点，所有控制走 mpv 的 JSON IPC
（`--input-ipc-server=\\.\pipe\dvplayer-<pid>-<n>`，`Player/MpvIpc.cs`）。

**实测**（`scripts/windows/verify-ipc.ps1`，外部另开一条管道读/写）：

| 动作 | 结果 |
| --- | --- |
| `get_property time-pos` | `5.756`（播放中） |
| `get_property duration` | `20.728` |
| `get_property video-params/pixelformat` | `d3d11` |
| `get_property current-tracks/video/dolby-vision-profile` | `7` |
| `current-tracks/video/dolby-vision-level` | `6` |
| `set_property pause true` | 生效（`pause` 变 `true`） |
| `seek 14 absolute` | `time-pos` → `14.014` |
| 壳里按 Space（焦点在主窗） | `pause` → `true` |

两个踩过的坑：

1. **`dolby-vision-profile` 没有顶层属性**，`get_property dolby-vision-profile`
   返回 `property not found`，必须走 `current-tracks/video/...`。
2. **回复要按 `request_id` 匹配**：mpv 会把上一条命令的回复和后一条混在一起，
   不匹配就会读到旧值（之前一度误判 `set pause` 无效）。

控制条在视频下方单独一行（WPF 元素压不到 `HwndHost` 上，airspace），
九列：打开 / 播放暂停 / 当前时间 / 进度条 / 总时长 / DV 徽标 / VOL / 音量 / 全屏。

**FEL/MEL 徽标**（ADR-0005）：mpv 不暴露 `disable_residual_flag`，所以壳里
加了一条侧路 `Player/DolbyVisionProbe.cs`：

```text
ffmpeg -map 0:v:0 -c copy -t 3 -f hevc   # 抽 3 秒码流（单轨带内交织：BL/EL/RPU 都在）
dovi_tool extract-rpu                    # 扫 NAL type 62 抓 RPU
dovi_tool info -f 0                      # 读 dovi_profile + el_type
```

关键结论：**单轨带内交织的 P7 不需要先拆 EL**，`extract-rpu` 直接能吃整条
码流（4K 3 秒约 10 MB，`ffmpeg` < 1 s）。双轨封装才需要试第二轨。
结果按「路径 + 大小 + mtime」缓存在 `%LOCALAPPDATA%\dvplayer\dvprobe.json`，
第二次播放不再起进程。实测徽标 `DV P7 (FEL)`，`disable_residual_flag=false`。

**还没验**：多显示器（需要外接第二块屏）、外接 HDR 屏的 HDR 输出。

### 2026-11-19 A8：蓝光 ISO 原盘与选集

样本 `HUSH_2IN1_PURE.ISO`（33.5 GiB，NAS `10.0.0.100` 下载到 `D:\dvplayer\iso\`）。

**不挂载直读**：`mpv --bluray-device=<iso> bd://` 直接打开，libbluray 打印：

```
[bd] idx:   0 duration: 01:21:46 angles:  1 (playlist: 00001.mpls)
[bd] idx:   1 duration: 01:21:46 angles:  1 (playlist: 00002.mpls)
[bd] First play: 1, Top menu: 1, HDMV Titles: 2, BD-J Titles: 0, Other: 0
```

**自读 mpls**（`iso-titles.ps1`）算出两个 4907.0s 正片，与 libbluray 的
01:21:46.985 差 0.015s；章节数 13 与 libbluray 的 `chapter-list/count` 一致。

1. **MPLS 是大端**，`[BitConverter]` 按小端读会把时长读成垃圾；

3. `PlayItem` 的 `length` **不含自身 2 字节**，下一项 = 当前位置 + 2 + length；
   章节 mark 是**定长 14 字节**，没有逐项 length，mark 数在段头 `+4`。

**选集**（`--msg-level=bd=trace` 看实际打开的流）：

| 目标 | 打开 |
| --- | --- |
| `bd://mpls/1` | `BDMV\STREAM\00001.m2ts` |
| `bd://mpls/2` | `BDMV\STREAM\00002.m2ts` |
| `--edition=1 bd://` | `cfg_title=1`（title 2） |

注意 `bd://mpls/00001.mpls` 会报 `number expected: '.mpls'`，**只能写纯数字**。

音轨 DTS，字幕 3 条 PGS（eng / zho / zho）。

**章节**：两个正片各 13 章，与 libbluray 的 `chapter-list/count` 一致。
