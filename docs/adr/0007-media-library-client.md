# ADR-0007：正式壳是媒体库聚合客户端

- 状态：已定
- 日期：2026-11-19

## 背景

M0 的 `DvPlayer.Windows` 只是为了验收 mpv 嵌入、IPC、DV 徽标和全屏，
里面写死了默认样片、控制条布局也是验证性质的。正式产品不能在这个壳上继续加。

产品形态由用户确定：

- 主界面以**媒体库**为中心，不是文件浏览器；
- 同时接**飞牛影视（fnOS Media）**与 **Emby**（后续 Jellyfin / Plex）；
- 支持**合并搜索**，统一展示各源的播放记录与进度；
- 交互与视觉以「媒体库优先、卡片化、深色」为基调。

## 决策

1. 新建正式项目 `apps/windows/DvPlayer`，不复用 M0 壳的页面与布局；
   只把与 UI 无关的 `Player/`（mpv 进程、JSON IPC、DV 探测）搬过去。
2. 用**适配器**接各媒体服务器：

   ```
   IMediaSource
     ├── FnOsSource    (飞牛影视 /v/api/v1，需 authx 签名)
     └── EmbySource    (Emby 标准 API，X-Emby-Token)
   ```

3. 统一模型只有四个：`MediaLibrary`、`MediaItem`、`PlayRecord`、`PlaySource`（可播地址）。
4. 聚合层负责合并、去重、排序与搜索；UI 只认统一模型，不认具体服务器。
5. 播放仍然交给 mpv（ADR-0001），播放地址由各源给出（直链或转码流）。

## 为什么不是文件优先

用户要的是“打开就是片库、能看到各源的播放记录”，文件树只是补充。
服务器首页 / 资源 / 记录 / 设置四个入口正好对上。

## 后果

- 需要维护各服务器的 API 适配，飞牛的签名逻辑已经逆向并记录在
  [docs/FNOS-API.md](../FNOS-API.md)；
- 图片缓存、分页、失败重试要统一做在聚合层；
- M0 的 `DvPlayer.Windows` 保留为验证用，不再作为产品入口。
